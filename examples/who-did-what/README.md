# who-did-what — who logged in, who became root, what they ran

> 🌐 **English** · [Tiếng Việt](../../docs/vi/examples/who-did-what.md)

A read-only report for a server that several people administer. One command answers the questions you ask after something goes wrong:

- **Who logged in over SSH, and with which key?**
- **Who became root (or another user), and what did they run with `sudo`?**
- **What did each person run, even inside a root shell opened with `sudo -i`?**
- **Who changed a watched file, such as `/etc/nginx/nginx.conf`?**

It reads the systemd journal and the Linux audit log, and **never changes anything** on the system. It complements PAMSignal: PAMSignal alerts you the moment someone logs in or becomes root; `who-did-what` shows you what they did afterwards.

> This is an example, not part of the `pamsignal` package. Copy it to the servers where you want it.

---

## What it needs

| Section | Source | Needs |
|---|---|---|
| `logins` | sshd's journal entries | Nothing extra |
| `sudo` | sudo's and su's journal entries | Nothing extra |
| `commands` | auditd records keyed `user-cmd` | The command-logging rules from [SSH hardening, section 2.3](../../docs/ssh-hardening.md#23-what-they-typed-inside-a-root-shell) |
| `files` | auditd file watches (`-w … -k …`) | The file watches from [SSH hardening, section 2.4](../../docs/ssh-hardening.md#24-who-changed-which-file) |

A section whose source is missing prints a short note pointing at the right section of the guide, and the rest of the report still runs.

Tested on Ubuntu 24.04 with a real kernel (the audit sections cannot run in a container or under WSL2). It needs `bash`, GNU `date`, `awk`, `journalctl` and, for the audit sections, `ausearch` and `auditctl`.

## Install

```bash
sudo install -m 755 who-did-what.sh /usr/local/sbin/who-did-what
```

## Use

Run it with `sudo`: other users' journal entries and the audit log are readable only by root.

```bash
sudo who-did-what                                  # everything, today
sudo who-did-what --since "2 hours ago"            # a shorter window
sudo who-did-what --user alice --since yesterday   # one person
sudo who-did-what files --since "2026-11-24 09:00" --until "2026-11-24 12:00"
sudo who-did-what --help
```

`--since` and `--until` accept anything GNU `date` understands: `today`, `yesterday`, `"2 hours ago"`, `"2026-11-24 09:00"`.

## Sample output

From the test VM (`--user alice`, trimmed):

```text
== Logins (SSH) ==
  TIME                      USER         FROM                   METHOD     KEY
  2026-11-24T04:25:05+00:00 alice        127.0.0.1:58666        publickey  SHA256:L3vJ… (not in any authorized_keys)
  2026-11-24T04:27:09+00:00 alice        127.0.0.1:42870        publickey  alice: alice@laptop

== Became another user (sudo, su) ==
  TIME                      WHO          AS       TSID   COMMAND / EVENT
  2026-11-24T04:27:09+00:00 alice        root     00000G /usr/bin/systemctl is-active ssh
  2026-11-24T04:27:10+00:00 alice        root     00000H /bin/bash

== Commands (auditd, by login ID) ==
  TIME                WHO        AS       SES   TTY    COMMAND
  2026-11-24T04:27:10 alice      alice    40    (none) sudo -S -i
  2026-11-24T04:27:10 alice      root     40    (none) -bash
  2026-11-24T04:27:10 alice      root     40    (none) systemctl is-active cron
  2026-11-24T04:27:10 alice      root     40    (none) rm -f /var/www/old.html
  (records generated by every login are hidden; --raw shows them)

== Changes to watched files (auditd) ==
  TIME                WHO        AS       ACTION   KEY            VIA          PATH
  2026-11-24T04:27:10 alice      root     delete   webroot        rm           /var/www/old.html
  2026-11-24T04:27:10 alice      root     write    nginx-config   bash         /etc/nginx/nginx.conf
```

How to read it:

- **`WHO alice` / `AS root`** — alice, acting as root. The audit log records the login ID set when alice logged in, which `sudo` and `su` do not change, so commands typed inside `sudo -i` still carry her name.
- **`SES`** groups everything from one login session; **`TSID`** is the sudo session ID you can replay with `sudo sudoreplay <TSID>` if [session recording](../../docs/ssh-hardening.md#23-what-they-typed-inside-a-root-shell) is on.
- **`(not in any authorized_keys)`** — the key used for that login is no longer in any `authorized_keys` file. Expected after you remove someone's key; worth investigating if you didn't.
- **`/etc/nginx/nginx.conf` written via `bash`** — the change came from a shell redirection (`echo … >> file`), which is why it shows up only under files and not under commands: shell built-ins don't start a program.

## Things to know

- **Login background is hidden by default.** Every login runs programs of its own: the message of the day, the systemd user session, shell start-up checks. In each session, programs run as root *before* the person's own shell started are login machinery (the person could not have run anything yet), so they are hidden, along with a few known start-up commands. `--raw` shows everything.
- **Output is made safe for your terminal.** Log entries contain text other people chose (usernames, command arguments). Control characters are replaced with `?`, so nothing in a log line can clear your screen or rewrite what you see.
- **It only reads what is on this server.** Someone who gained root can delete local logs. Keep a copy off the server ([SSH hardening, section 2.6](../../docs/ssh-hardening.md#26-keep-the-trail-where-an-intruder-cant-erase-it)) and run your investigation there when it matters.
- **Journal retention limits how far back you can look.** Check `journalctl --disk-usage` and the audit log rotation (`max_log_file`, `num_logs` in `/etc/audit/auditd.conf`).

## Tests

`tests/e2e.sh` builds a small scenario on a real machine — two users with SSH keys, sudo session recording and the audit rules from the guide, a root shell, file edits, a refused `sudo`, a command argument carrying a terminal escape sequence — and checks the report line by line.

It **installs openssh-server and auditd, creates users, and changes the sudo and audit configuration**, so run it only on a throwaway VM or a CI runner:

```bash
sudo bash examples/who-did-what/tests/e2e.sh
```

CI runs it on every pull request (`.github/workflows/ci.yml`), together with `shellcheck`.
