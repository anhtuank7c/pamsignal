# who-did-what — ai đã đăng nhập, ai đã lên root, họ đã chạy gì

> 🌐 [English](../../../examples/who-did-what/README.md) · **Tiếng Việt**

Một báo cáo chỉ đọc dành cho server có nhiều người cùng quản trị. Chỉ một lệnh trả lời những câu hỏi bạn sẽ hỏi khi có sự cố:

- **Ai đã đăng nhập SSH, và bằng key nào?**
- **Ai đã lên root (hoặc sang user khác), và đã chạy gì bằng `sudo`?**
- **Mỗi người đã chạy những gì, kể cả bên trong shell root mở bằng `sudo -i`?**
- **Ai đã sửa một file đang được theo dõi, như `/etc/nginx/nginx.conf`?**

Nó đọc systemd journal và audit log của Linux, và **không bao giờ thay đổi bất cứ thứ gì** trên hệ thống. Nó bổ trợ cho PAMSignal: PAMSignal báo cho bạn ngay khi có người đăng nhập hoặc lên root; `who-did-what` cho bạn thấy họ đã làm gì sau đó.

> Đây là một ví dụ, không thuộc package `pamsignal`. Hãy copy nó lên những server bạn muốn dùng.

---

## Cần những gì

| Phần | Nguồn | Cần thêm |
|---|---|---|
| `logins` | Các entry journal của sshd | Không cần gì thêm |
| `sudo` | Các entry journal của sudo và su | Không cần gì thêm |
| `commands` | Bản ghi auditd có key `user-cmd` | Các rule ghi lệnh trong [Bảo mật SSH, mục 2.3](../ssh-hardening.md#23-họ-đã-gõ-gì-bên-trong-shell-root) |
| `files` | File watch của auditd (`-w … -k …`) | Các file watch trong [Bảo mật SSH, mục 2.4](../ssh-hardening.md#24-ai-đã-sửa-file-nào) |

Phần nào thiếu nguồn sẽ in một ghi chú ngắn chỉ tới đúng mục trong hướng dẫn, và phần còn lại của báo cáo vẫn chạy bình thường.

Đã test trên Ubuntu 24.04 với kernel thật (các phần audit không chạy được trong container hay dưới WSL2). Nó cần `bash`, GNU `date`, `awk`, `journalctl`, và với các phần audit thì cần thêm `ausearch` và `auditctl`.

## Cài đặt

```bash
sudo install -m 755 who-did-what.sh /usr/local/sbin/who-did-what
```

## Sử dụng

Chạy bằng `sudo`: entry journal của user khác và audit log chỉ root mới đọc được.

```bash
sudo who-did-what                                  # everything, today
sudo who-did-what --since "2 hours ago"            # a shorter window
sudo who-did-what --user alice --since yesterday   # one person
sudo who-did-what files --since "2026-11-24 09:00" --until "2026-11-24 12:00"
sudo who-did-what --help
```

`--since` và `--until` nhận mọi cách viết mà GNU `date` hiểu: `today`, `yesterday`, `"2 hours ago"`, `"2026-11-24 09:00"`.

## Output mẫu

Từ VM test (`--user alice`, đã rút gọn):

```text
== Logins (SSH) ==
  TIME                      USER         FROM                   METHOD     KEY
  2026-11-24T04:25:05+00:00 alice        127.0.0.1:58666        publickey  SHA256:L3vJ… (not in any authorized_keys)
  2026-11-24T04:27:09+00:00 alice        127.0.0.1:42870        publickey  alice: alice@laptop

== Became another user (sudo, su) ==
  TIME                      WHO          AS       TSID   COMMAND / EVENT
  2026-11-24T04:27:09+00:00 alice        root     00000G /usr/bin/systemctl is-active ssh
  2026-11-24T04:27:10+00:00 alice        root     00000H /bin/bash

== Commands (auditd, by login ID) ==
  TIME                WHO        AS       SES   TTY    COMMAND
  2026-11-24T04:27:10 alice      alice    40    (none) sudo -S -i
  2026-11-24T04:27:10 alice      root     40    (none) -bash
  2026-11-24T04:27:10 alice      root     40    (none) systemctl is-active cron
  2026-11-24T04:27:10 alice      root     40    (none) rm -f /var/www/old.html
  (153 records generated by logins themselves are hidden; --raw shows them)

== Changes to watched files (auditd) ==
  TIME                WHO        AS       ACTION   KEY            VIA          PATH
  2026-11-24T04:27:10 alice      root     delete   webroot        rm           /var/www/old.html
  2026-11-24T04:27:10 alice      root     write    nginx-config   bash         /etc/nginx/nginx.conf
```

Cách đọc:

- **`WHO alice` / `AS root`** — alice, đang hành động với quyền root. Audit log ghi login ID được đặt khi alice đăng nhập, và `sudo` hay `su` đều không đổi được nó, nên các lệnh gõ trong `sudo -i` vẫn mang tên cô ấy.
- **`SES`** gom mọi thứ thuộc một phiên đăng nhập; **`TSID`** là ID phiên sudo mà bạn có thể phát lại bằng `sudo sudoreplay <TSID>` nếu đã bật [ghi lại phiên](../ssh-hardening.md#23-họ-đã-gõ-gì-bên-trong-shell-root).
- **`(not in any authorized_keys)`** — key dùng cho lần đăng nhập đó không còn nằm trong file `authorized_keys` nào. Bình thường nếu bạn vừa gỡ key của ai đó; đáng điều tra nếu bạn không làm việc đó.
- **`/etc/nginx/nginx.conf` được ghi qua `bash`** — thay đổi đến từ một lệnh chuyển hướng của shell (`echo … >> file`), nên nó chỉ hiện ở phần files chứ không ở phần commands: lệnh có sẵn của shell không khởi chạy chương trình nào.

## Những điều cần biết

- **Chỉ bản ghi nền của lúc đăng nhập mới được ẩn theo mặc định.** Mỗi lần đăng nhập tự chạy một số chương trình: message of the day, phiên systemd của user, các bước kiểm tra lúc shell khởi động. Báo cáo ẩn những chương trình chạy với quyền root *trước khi* shell của chính người đó khởi động, trong các phiên đăng nhập nằm trong khoảng thời gian đang xem (người đó chưa thể chạy gì vào lúc ấy), cùng với vài chương trình hỗ trợ của systemd được nhận diện qua đường dẫn binary thật do kernel ghi. Không có gì bị ẩn chỉ vì nội dung dòng lệnh, nên đặt tên lệnh là `update-motd` cũng không giấu được nó. Báo cáo cho biết đã ẩn bao nhiêu bản ghi; `--raw` hiện tất cả.
- **Dòng log giả bị bỏ qua.** User nào cũng có thể dùng `logger` để ghi một dòng gắn nhãn `sshd` hay `sudo`. Báo cáo chỉ đọc entry do sshd chạy bằng root và do chính binary `sudo`/`su` thật ghi (các trường `_UID` và `_EXE` của journald, lấy từ kernel), và chỉ coi một message của sshd là lần đăng nhập khi nó *bắt đầu* bằng `Accepted` — một lần thử thất bại với username `Accepted password for root from …` không được tính.
- **Dòng sudo nhập nhằng được đánh dấu, không đoán.** sudo ghi thư mục làm việc trước `USER=` và lệnh sau `COMMAND=`, mà cả hai đều do người dùng chọn. Một thư mục tên `/tmp/x ; USER=nobody ; COMMAND=/bin/true` khiến dòng log có hai cách đọc, nên dòng đó hiện ra dưới dạng `[AMBIGUOUS …]` với `?` ở cột user và TSID. Phần `commands` (auditd) không bị ảnh hưởng và cho thấy lệnh thực sự đã chạy.
- **Output an toàn cho terminal của bạn.** Entry log chứa chuỗi do người khác chọn (username, tham số lệnh). Ký tự điều khiển được thay bằng `?`, nên không dòng log nào có thể xóa màn hình hay sửa những gì bạn đang thấy.
- **Nó chỉ đọc những gì có trên server này.** Ai đó đã chiếm được root có thể xóa log cục bộ. Hãy giữ một bản sao ngoài server ([Bảo mật SSH, mục 2.6](../ssh-hardening.md#26-giữ-dấu-vết-ở-nơi-kẻ-xâm-nhập-không-xóa-được)) và điều tra trên bản sao đó khi chuyện quan trọng.
- **Thời gian lưu journal giới hạn bạn xem lại được bao xa.** Kiểm tra `journalctl --disk-usage` và cách xoay vòng audit log (`max_log_file`, `num_logs` trong `/etc/audit/auditd.conf`).

## Test

`tests/e2e.sh` dựng một kịch bản nhỏ trên máy thật — hai user có SSH key, ghi lại phiên sudo và các audit rule trong hướng dẫn, một shell root, sửa file, một lần `sudo` bị từ chối, một tham số lệnh chứa chuỗi escape của terminal, và các lần thử giả mạo hay che giấu dấu vết — rồi kiểm tra từng dòng của báo cáo.

Nó **cài openssh-server và auditd, tạo user, và thay đổi cấu hình sudo và audit**, nên chỉ chạy trên VM dùng xong bỏ hoặc CI runner:

```bash
sudo bash examples/who-did-what/tests/e2e.sh
```

CI chạy nó ở mỗi pull request (`.github/workflows/ci.yml`), cùng với `shellcheck`.
